# Overview
Enhance the existing cc-obsidian-mem MCP server by integrating basic-memory knowledge graph features (semantic parsing, memory:// URLs, bidirectional sync) using Supabase for cloud sync and multi-device support, with Supabase Auth as primary authentication and custom OAuth 2.0 as fallback, following MCP best practices from awesome-claude-code.

The goal is to create a production-ready MCP server that combines the best features of both cc-obsidian-mem and basic-memory, with cloud synchronization capabilities and flexible authentication options.

# Core Features

## Knowledge Graph System
- Parse Markdown files to extract Entities, Observations, and Relations
- Maintain PostgreSQL database (via Supabase) for fast queries and indexing
- Support memory:// URL scheme for entity references
- Bidirectional sync between Markdown files and knowledge graph
- Real-time synchronization across devices using Supabase subscriptions

## Authentication System
- Supabase Auth as primary authentication (handles OAuth providers automatically)
- Custom OAuth 2.0 fallback for advanced use cases
- Support for multiple providers (Google, GitHub, generic OAuth 2.0)
- Token validation and refresh logic
- Dynamic Client Registration for Claude.ai integration

## Enhanced MCP Tools
- build_context - Navigate knowledge graph via memory:// URLs
- canvas - Generate knowledge visualizations
- recent_activity - Find recently updated information
- Enhanced mem_search - Search both files and knowledge graph
- Enhanced mem_write - Auto-extract Observations and Relations from content
- Enhanced mem_read - Support memory:// URLs

## Cloud Sync & Multi-Device Support
- Real-time sync via Supabase subscriptions
- Row Level Security (RLS) for multi-user support
- Conflict resolution for concurrent edits
- Offline support with local caching

# User Experience

## Developer Personas

# Technical Architecture

## System Components

### Knowledge Graph Engine
- PostgreSQL database schema (via Supabase)
  - entities table (id, title, type, permalink, file_path, project, timestamps)
  - observations table (id, entity_id, category, content, tags, context, timestamps)
  - relations table (id, from_entity_id, to_entity_id, relation_type, context, timestamps)
- Markdown parser for semantic patterns
- Entity/Observation/Relation extraction from frontmatter and content
- Bidirectional sync engine (file changes → DB, DB queries → file updates)

### Authentication Layer
- Supabase Auth integration (primary)
  - Handles OAuth providers (Google, GitHub, etc.)
  - Email/password authentication
  - Session management
- Custom OAuth 2.0 provider (fallback)
  - Authorization code flow with PKCE
  - Token validation and refresh
  - Dynamic Client Registration endpoint

### MCP Server
- Stdio transport for local use
- HTTP/SSE transport for remote deployments
- Tool registration and execution
- Real-time sync via Supabase subscriptions

### File Format Support
- Obsidian format (existing) - Frontmatter, wikilinks, Dataview
- Basic Memory format (new) - Semantic patterns with Observations and Relations
- Bidirectional conversion between formats

## Data Models

### Entity
```typescript
interface Entity {
  id: string;
  title: string;
  type: 'note' | 'session' | 'error' | 'decision' | 'pattern' | 'file' | 'learning';
  permalink: string;
  file_path: string;
  project?: string;
  created_at: Date;
  updated_at: Date;
```

### Observation
```typescript
interface Observation {
  id: string;
  entity_id: string;
  category: string;
  content: string;
  tags: string[];
  context?: string;
  created_at: Date;
}
```

### Relation
```typescript
interface Relation {
  id: string;
  from_entity_id: string;
  to_entity_id: string;
  relation_type: string;
  context?: string;
  created_at: Date;
}
```

# Logical Dependency Chain

2. **Knowledge Graph Foundation** (Phase 2) - Core functionality, needed before tools
3. **Authentication** (Phase 3) - Can be done in parallel with Phase 2, but needed for remote access

## Building on Foundation

5. **Integration & Testing** (Phase 5) - Requires all previous phases complete
6. **Documentation** (Phase 6) - Can be written in parallel, finalized after Phase 5

Supabase Setup → Knowledge Graph → Tools → Integration → Documentation

Authentication can be developed in parallel with Knowledge Graph, but both must complete before Integration phase.

# Risks and Mitigations

## Technical Challenges

### Risk: Supabase free tier limitations
- **Impact**: May hit database size or bandwidth limits
- **Mitigation**: Monitor usage, implement data archiving, plan for upgrade path

### Risk: Real-time sync conflicts
- **Impact**: Concurrent edits may cause data loss
- **Mitigation**: Implement conflict resolution strategy, use Supabase's built-in conflict handling

### Risk: Performance with large vaults
- **Impact**: Slow queries with 1000+ notes
- **Mitigation**: Proper indexing, query optimization, pagination, caching

### Risk: OAuth 2.0 complexity
- **Impact**: Difficult to implement correctly, security concerns
- **Mitigation**: Use Supabase Auth primarily, custom OAuth as fallback only, follow OAuth 2.1 best practices

## MVP Considerations

### MVP Scope
- Phase 1: Supabase Setup (essential)
- Phase 2: Knowledge Graph Foundation (core feature)
- Phase 3: Supabase Auth only (simplified authentication)
- Phase 4: Basic tools (mem_search, mem_write enhancements)
- Phase 5: Basic integration (skip advanced testing)
- Phase 6: Minimal documentation

### Post-MVP Enhancements
- Custom OAuth 2.0 fallback
- Advanced tools (canvas, build_context)
- Comprehensive testing suite
- Full documentation

## Resource Constraints
- Free tier Supabase limits
- Development time for complex features
- Testing across multiple devices

**Mitigation**: Start with MVP, iterate based on user feedback, prioritize most valuable features first.
